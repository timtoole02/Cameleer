# Cameleer Production App Rebuild Mandate

You are no longer allowed to make random UI patches, cosmetic changes, one-off scripts, fake demos, or placeholder workflows.

Cameleer currently presents itself as an enterprise agentic AI workspace, but it does not behave like one. Your job is to turn it into an actual production app with working architecture, durable state, predictable agent behavior, clean UI, test coverage, and a clear release gate.

Do not optimize for screenshots. Do not optimize for looking impressive. Optimize for a working app that can be opened, used, closed, reopened, and trusted.

## Core Product Definition

Cameleer is a local-first enterprise agent workspace powered by Camelid and compatible model backends.

The production app must support:

1. A real agent registry
2. A real nested agent org chart
3. A real chat workspace
4. A real task and Kanban system
5. A real backlog
6. Real shared memory
7. Real project context
8. Real model profiles
9. Real runtime execution state
10. Real tool execution records
11. Real audit logs
12. Real persistence across app restarts
13. Real error handling
14. Real settings
15. A working macOS Tauri app build

Nothing counts as done unless it is persisted, reloadable, visible in the UI, and covered by at least one test or reproducible manual verification step.

## Hard Reset Rules

Before adding features, clean up the repo.

Remove or quarantine all one-off repair scripts from the production path. Files like `fix_app`, `replace_app`, `rewrite_app`, `update_task`, and similar scripts are not production architecture. If any are still useful, move them to `tools/legacy-repair/` with a README explaining they are not part of runtime or build.

Remove template language from the app README and internal docs. The project must no longer look like a Tauri starter template.

Do not keep giant monolithic frontend files. Split the app by domain.
